Real models, real recorded answers, every number reproducible

Most benchmark questions are not worth asking. These are.

Choosing between AI models means running a benchmark: a few thousand questions, put to every model on the shortlist, counted up into a percentage. Twenty models is sixty thousand paid calls, and it has to be repeated every time any vendor ships anything. Most of those questions separate nobody. Standardised testing worked this out decades ago and stopped handing everybody the same fixed paper. This page does the same thing to a language model benchmark, on real recorded answers, and lets you watch it happen.

Run the test on two real models

Twelve current models from four vendors and a laptop, 2,816 scored questions, and the answers the models actually gave, recorded in September 2026 by putting the 3,000-question suite to them for US$18.25. The adaptive test runs in your browser against those answers; it can only replay what was asked and paid for, and it never invents a response. Every number can be reproduced from the public repository. See how it's built, in three diagrams.

The idea in one table

A benchmark score is a count of correct answers. A count cannot tell these five kinds of question apart, so it treats them as equal evidence about which model to buy.

What a question doesWhat it tells you about which model to buyWhat a percentage does with it
Every model gets it rightNothing. It separates nobodyCounts it, at full weight
Every model gets it wrongNothing. It separates nobodyCounts it, at full weight
Its stored answer key is wrongWorse than nothing: it penalises the models that were rightCounts it, at full weight
It leaked into training dataMeasures memory, not capabilityCounts it, at full weight
It cleanly separates stronger models from weaker onesThis is the entire signal you are paying forCounts it, at full weight

Nobody knows which of a benchmark's questions belong to which row, because results are published as one aggregate and the per-question detail is thrown away. Item response theory, the statistics behind the GRE and every professional licensing exam, measures each question first: how hard it is, and how sharply it separates ability just above its threshold from ability just below. Once each question carries those two numbers, the test can be short, because you can ask the question that tells you the most about this particular model and stop when the answer is decided.

Run the test yourself

Pick two models. The test asks one question at a time: after each answer it updates what it believes about each model, then chooses the next question to be the one that will tell it the most about them at their current level. Beside it, the same two models are asked questions drawn at random from the same suite. Same models, same budget, same recorded answers, and the only difference is which questions get asked.

Try anthropic-sonnet against openai-frontier, which the method cannot settle. Both estimates run to the end of the bank's ability scale and stop there, because the selector asks for questions it believes are a coin flip at that level and these two get about nine in ten of them right. Only 253 of the 2,816 questions are harder than +3, so the suite has run out of questions that could tell them apart, and the tight-looking interval is a wall rather than evidence. The item parameters were fitted on 150 models evaluated between 2023 and 2025; a bank calibrated on that panel measures the top of a 2026 shortlist poorly, which is a limit of this bank rather than of the method, and it is the reason the page draws the edge of the scale instead of leaving you to notice the curve is flattened against it.

If two models never separate, that is still an answer: at that budget they are indistinguishable, so choose on price, latency or context window.

Watch the difficulty column. The test starts near the middle of the scale, and as it learns that a model is strong it stops wasting questions the model will certainly get right. A negative discrimination in that table is not a mistake either: the selector treats information as information, and an item whose fitted slope runs backwards still carries some. It is also the signature of a wrong answer key, which is why the repository publishes a list of them rather than quietly dropping them here.

For the technical reader: where the answers and the dollars come from

Three of the twelve cost nothing in dollars, and they are not free. The three models on a laptop were billed in hours rather than tokens: the full suite took nine hours of laptop CPU for the 7B, against about an hour for a hosted model over the network, and that machine can do nothing else meanwhile. Both figures come from the same ledger, which recorded a price and a latency for every call, so a short test is priced in whichever currency the model is actually paid for. The three Anthropic models have no per-call time at all, because this project sends them through the Message Batches endpoint at half price and a call inside a batch has no latency worth reporting; the page says so rather than showing a zero.

Nothing here is simulated. The answers are the ones the twelve models gave when they were administered the frozen suite in September 2026, one bit per cell, and the dollars are the ones the gateway's ledger recorded for those exact calls. The arithmetic, about two hundred lines, is in irt.js beside this page. The item parameters were fitted to 150 other models from a public evaluation archive, and not one of the twelve models here was in that fit, so the questions were measured before these models existed.

How it works

From a public archive of answers to a ten-question test

The rest of this page is the method and its evidence, in the order it happens. Each part starts in plain language, with a picture. Where there is more to say for someone who builds models for a living, it is folded away under For the technical reader, so you can skip it if you only want the idea.

The whole idea in one picture

Six steps. The order matters: every question is measured on other models first, so the twelve models on this page are tested by a bank that has never seen them.

  1. 1GatherPublic per-question results from HELM and the Open LLM Leaderboard.
  2. 2FreezeTwo banks of questions, fetched once and fingerprinted.
  3. 3CalibrateGive every question a difficulty and a sharpness, by item response theory.
  4. 4AskPut the question that tells the most about this model, one at a time.
  5. 5StopWhen the two models' ranges no longer overlap, or the budget runs out.
  6. 6CheckAgainst twelve current models the fit never saw.

The questions were measured before the models were. Not one of the twelve models on this page was in the fit, so the test is judged on models it had never seen.

Where it wins, and where it stops winning

This is the whole result: how closely a short test reproduces the ranking a full benchmark produces, against the number of questions it was allowed, with a bootstrap interval on every point. The dashed line is what the same budget buys spent at random.

Above roughly two hundred questions, adaptive selection stops winning and a plain random sample catches it. The two are measuring different things: the adaptive test converges on the bank's ability scale, while a leaderboard reports the suite average, and even with every question in hand those two rankings agree only to about 0.92. If you want the benchmark's own average, sample at random and score it directly. If you want to know which model is better, ask ten well-chosen questions.

How many questions does your decision actually need?

This is the step almost everybody skips, and it is where an evaluation budget goes. Before spending anything, ask what size of difference the decision turns on. If your candidates are about a point apart, no affordable test will separate them, and learning that first is itself a result.

One question in five is measuring nothing

Every dot is one question from the bank of 20,365. Across: how hard it is. Up: how sharply it separates stronger models from weaker ones. Everything in the shaded band is close to a coin flip for everybody, and everything below zero runs backwards, meaning stronger models get it wrong more often, which is the signature of a wrong answer key.

A negative slope has four possible causes and they are not equally interesting: a wrong answer key, an ambiguous question where the better model sees the ambiguity, a grader marking a correct answer wrong, and genuine inverse scaling. Telling them apart needs the question text and a person, so nothing here is published as mis-keyed. But one fit produces the list, and if you own a benchmark it is where to look first: those questions are free to find and they cost you money on every run.

Three things a single score cannot tell you

The same twelve models, measured three more ways. Each of these is cheap to run and almost nobody publishes them, which is why a two-point drop in a leaderboard gets a headline it has not earned.

What the data proved wrong

The first thing the measurements rejected was the project's own headline assumption. Each rejection is in the repository with its evidence. A few of them:

Adaptive testing as a drop-in for the benchmark score

The plan expected random sampling to fail. Above about two hundred questions it catches up: the adaptive test estimates ability, and a leaderboard reports an average.

The evaluation software's own hash as a question's ID

It hashes the software's version of the question, so it moves when the software does. On one maths benchmark a quarter of the panel disagreed on all 154 hashes while the question text was identical.

A heavyweight fitting library

py-irt and PyMC were planned. Bock-Aitkin EM in NumPy fits the whole matrix exactly in under a minute, without a 1.5 GB PyTorch dependency.

"Diagrams sent as drawing code are unanswerable"

They are not. Models scored 0.733 on those 44 MATH items against 0.808 on the rest, with overlapping intervals: they read the code.

The project's own headline assumption is written up in full as rejected. Read it here.

What this does not do

It scores right or wrong, and nothing else

No writing quality, no human preference, and no second model acting as a judge. The psychometrics rests on a correct-or-not response, and a judge would add a second, drifting instrument to the measurement.

Questions are not independent, and that is measured

Between 8 and 31 percent of question pairs, depending on the benchmark, are correlated beyond what ability explains. Every interval from a fixed-length benchmark is therefore optimistic, including some of this project's own, and the correction ships with the bank.

Twelve models is twelve models

The live half of this page rests on twelve models spanning 0.54 to 0.94 accuracy across four vendors and a laptop. That settles that the question parameters transfer at all. It is too few to rank methods against each other, and every interval in it is wide and published wide.

A second bank, from a different source, says the same

A result measured on one panel is a result about that panel, so the whole method was run again on 400 open-weight models from a different source, scored by different evaluation software. The shape replicates and so does the ceiling. Item parameters transfer between the two only after the questions that measure nothing are dropped.

For the technical reader: the choices that are easy to get wrong
  • The twelve test models are held out of every fit. The item parameters come from 150 other models, read and not refitted, so the transfer result is on models the bank had never seen.
  • Two banks, from different sources. 400 open-weight models from the Open LLM Leaderboard repeat the whole method, and the 998 questions the two banks share put a number on whether difficulty carries over.
  • Questions are not independent, and the correction ships. Local dependence is measured per benchmark (8% to 31% of pairs above Q3 0.2), and the power calculation treats its answers as a floor.
  • Every paid call goes through one gateway that caps spend and records a price and latency per call, so a short test is priced from the ledger rather than estimated.
  • The page replays; it never invents. The adaptive test in the browser can only ask questions whose recorded answers exist.

How this was built

I designed this project and made the calls in it: what to calibrate on, how to test the method, and what to do when a measurement disagreed with the plan. The call I would defend hardest is the second bank. A result measured on one panel of models is a result about that panel, so I ran the whole method again on questions from a different source, scored by different software, on a different kind of model, and used the 998 questions the two banks share to put a number on whether question difficulty carries over. The other is that I paid to put twelve current models through the suite and kept all twelve out of the fit, so the test is judged on models it had never seen. The first thing the data rejected was my own headline assumption, that adaptive testing could replace the benchmark score at any budget. Past about two hundred questions it cannot, and the chart above shows where.

I used an AI coding assistant (Claude Code) for implementation and drafting, which is now standard practice in software, data science and machine learning work. Every number on this page can be reproduced from the repository with one command, and every answer the test replays is one a model actually gave.

Glossary
Item response theory
The statistics behind standardised exams. Each question gets a difficulty and a measure of how sharply it separates stronger test-takers from weaker ones, and each test-taker gets an ability on the same scale.
Discrimination
How sharply a question separates ability just above its difficulty from ability just below. Near zero, the question tells you almost nothing. Below zero, stronger models get it wrong more often, which is the signature of a wrong answer key.
Adaptive test
A test that picks each next question from the answers so far, asking whatever will tell it most about this test-taker at their current estimated level.
Ability scale
The scale item response theory puts every model and every question on. A model's ability is where it has an even chance on a question of that difficulty.
Kendall's tau
A measure of how far two rankings agree. 1 is the same order and 0 is no relation. Here it compares a short test's ranking of models with the full benchmark's.
Interval
The range the true value probably sits in. Two models are separated once their intervals stop overlapping.
Statistical power
How often a test of a given size catches a real difference of a given size. 80% power misses one real drop in five.
Bank
The set of calibrated questions the test draws from. This project has two, built from different sources.
